## 2. 시스템 개요

Stock Canary는 보유 종목과 포트폴리오의 위험을 재무 위험(ML, 4단계)과 주가 변동 위험(계산 지표, 5단계) 두 축으로 점검하고, 공시·보도자료·개인 평가 이력 기반 RAG 챗봇을 제공하는 서비스임. 매수·매도 추천 없이 위험 신호와 근거만 제공함. 시장 전체 변동성은 종목 등급과 별도로 배너(F-29)로 안내함.

| 항목 | 내용 |
| --- | --- |
| 사용자 | 국내 주식 3\~10종목을 보유한 직장인 초보 투자자 (투자 경력 1\~3년) |
| 판단 | 이번 주에 살펴봐야 할 종목이 있는지, 이유는 무엇인지, 지난주 대비 무엇이 달라졌는지 |
| 사용 맥락 | 주 1회, 5\~10분 안에 점검 |
| 핵심 원칙 | 두 축을 하나의 점수로 합산하지 않음. 결론·살펴볼 종목을 먼저 보여 주고 근거·상세 지표는 선택적으로 확인. 사실 근거는 공식 공시·보도자료 우선. LLM 문장의 수치는 원천 데이터와 대조. 체험 모드는 세션에만 보관하고 로그인 시에만 DB 저장. 매매 권유 차단, 모든 위험 평가는 참고 정보로 미래를 보장하지 않음 |
| 일정 | 기획안 발표 2026-12-01, EC2 배포 6주차(12/28 주), 경진대회 2027-01-08 |

## 3. 시스템 아키텍처

외부 데이터 수집, 지표·모델 산출, 공시 LLM 처리와 임베딩은 배치 파이프라인이 미리 수행하고, 서비스는 저장된 결과를 조회함. 실시간 LLM 호출은 종합평가 리포트와 챗봇 답변 두 가지로 한정함.

> 그림: 시스템 구성도 (외부 데이터 6종, 배치 모듈 4개(10단계), 저장소 2종, 서비스 2종). 원본 문서의 그림은 저장소에 포함되지 않음. 같은 구성은 `docs/system_architecture.md` 구성도 참고

파이프라인 결과는 PostgreSQL과 VectorDB에 적재되고, Backend는 이를 조회해 포트폴리오 지표와 챗봇 답변을 만듦. 파이프라인 실행 위치(EC2 cron 또는 로컬)는 미정이므로 EC2 경계 밖에 표시함. 특히 KIND 수집은 국내 IP 환경이 필요함.

### 설계 원칙

| 원칙 | 내용 |
| --- | --- |
| 사전 처리 | 수집, 재무 위험 추론, 주가 변동 위험 계산, 공시 분류·요약, 임베딩은 배치에서 수행 후 저장 |
| 조회 중심 서비스 | 서비스는 저장된 결과를 조회. 실시간 LLM 호출은 종합평가와 챗봇으로 한정 |
| 계층 독립성 | 수집이 실패해도 서비스는 마지막 적재 데이터로 동작 |
| 재실행 안전성 | 각 단계 upsert 적재로 재실행 시 중복 없음 |
| 두 축 분리 | 재무 위험과 주가 변동 위험을 별도 테이블·별도 등급으로 관리, 합산 점수 없음 |
| 개인 데이터 최소화 | 체험 모드는 세션에만 보관, 로그인 사용자만 DB 저장, 외부 LLM에는 비중·위험 요인만 전송 |

- 단계별 처리 흐름(평가 요청, 챗봇 질의)은 6-5\~6-7, 배포 구성은 9-3 참고

## 4. 기술 스택

### 주요 선택 근거

| 선택 | 근거 |
| --- | --- |
| 재무 위험은 ML, 주가 변동 위험은 계산 지표 | 재무 위험은 다변수 비선형 판별이 필요함. 주가 변동 위험은 과거 변동성이 근거로 충분하고 계산식을 사용자에게 그대로 제시 가능 |
| 주가 변동 위험은 시장 대비가 아닌 절대 변동성 | 시장 전체가 출렁일 때 종목 등급이 함께 오르는 것은 실제 위험 증가이므로 그대로 전달. 시장 전체 상황은 시장 변동성 배너(F-29)로 분리 안내 |
| 규칙 베이스라인·Merton·로지스틱·LightGBM 비교 | 기존 모형 대비 ML의 개선 폭을 성능 근거로 제시하기 위함 |
| FE·BE 분리 (FastAPI) | 계정·서버 세션·플로팅 챗봇 구현에 유리. Streamlit은 플로팅 UI에 커스텀 컴포넌트 필요 |
| 배치 사전 처리 + 조회 중심 서비스 | 실시간 LLM 호출을 종합평가·챗봇으로 한정해 비용과 EC2 부하를 제한 |
| 금감원 보도자료는 API, 나머지 보도자료는 크롤링 | 확인한 출처 중 금감원만 보도자료 API 제공. 금융위 RSS는 확인 시점에 점검 중, 정책브리핑 RSS는 미확인, 거래소는 목록 조회 응답(JSON)을 직접 사용 |

### VectorDB 선택 제안: pgvector

- 기존 PostgreSQL 재사용으로 컨테이너·볼륨 추가 없음. 이미지만 pgvector 포함 이미지로 교체
- `user_docs` 격리를 SQL `WHERE user_id = :session_user_id`로 강제 가능 (F-17)
- 데이터 삭제(T-10) 시 `user_reports` 행과 벡터를 같은 트랜잭션에서 삭제 가능. Chroma는 DB와 VectorDB 간 삭제 정합성을 별도로 보장해야 함
- 유의점: 벡터 인덱스 메모리 사용량을 EC2 사양 대비 사전 확인 필요

## 6. 모듈·기능 상세 명세

시스템은 배치 파이프라인 10단계와 서비스 기능 4종(포트폴리오 평가, 종합평가 리포트, RAG 챗봇, 세션·계정)으로 구성됨. 등급 기준값은 모두 예시값이며 라벨 집계·변동성 분포 확인 후 확정함.

### 6-1. 배치 파이프라인 단계

| 순서 | 단계 (`STEPS` 이름) | 모듈 | 주기 | 입력 | 처리 | 출력 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `collect_dart` | `pipeline/collect` | 일 (재무제표는 분기) | DART OpenAPI | 재무제표, 공시 목록·원문 수집 | `raw_financials`, `raw_disclosures` |
| 2 | `collect_kind` | `pipeline/collect` | 일 | KRX KIND (국내 IP 필요) | 관리종목·투자주의환기·거래정지 현재 목록, 투자주의·경고·위험 이력, 실질심사법인, 횡령 등 공시 | `raw_market_actions` 외 (7-2) |
| 3 | `collect_prices` | `pipeline/collect` | 일 | 공공데이터포털 주식시세, FinanceDataReader | 일별 주가·시가총액(최근 5년·일 갱신은 금융위 API, 2015년부터 과거 수정주가는 FinanceDataReader), KOSPI 지수, 상장폐지 목록·사유. 7-1 용도별 출처 참고 | `raw_prices`, `raw_delisting` |
| 4 | `collect_press` | `pipeline/collect` | 일 | 금융위 홈페이지, 금감원 API·홈페이지, 거래소 홈페이지, 정책브리핑 | 보도자료·소비자경보 수집, 첨부 PDF 본문 추출 | `raw_press_releases` |
| 5 | `build_mart_features` | `pipeline/process` | 주 | `raw_*` | 재무비율, 업종 평균, 상장 규정 근접도, 공시 이벤트 변수, Merton 부도거리 | `mart_features` |
| 6 | `price_risk` | `pipeline/process` | 주 | `raw_prices`, 시장조치 | 120거래일 변동성 등 주가 변동 지표 → 5단계 등급 | `mart_market_risk` |
| 7 | `market_volatility` | `pipeline/process` | 주 (토요일 결산) | KOSPI 지수 | 그 주 마지막 거래일 기준 20거래일 변동성, 주의(상위 10%)·경고(5.0%)·해제(상위 20%) 판정, 직전 결산 주 상태 기록 | `mart_market_volatility` |
| 8 | `score_financial_risk` | `ml/src` | 주 (학습은 연 1회) | `mart_features` | 보정 확률 → 4단계 등급, 규칙 덮어쓰기, 여유 구간 | `mart_fin_risk` |
| 9 | `classify_disclosures` | `pipeline/llm` | 일 | `raw_disclosures`, 소비자경보 | 공시 위험 유형 분류·3줄 요약. 소비자경보 대상 여부 분류도 이 단계에 배치 (제안) | `mart_disclosure_labels` |
| 10 | `embed_documents` | `pipeline/llm` | 일 | 위험 유형 공시, 보도자료 | 청킹, 임베딩 | `public_docs` |

공통 규칙

- 모든 적재는 UNIQUE 키 기반 upsert. 재실행 시 중복 적재 없음
- 모든 변수는 공시일 기준 정렬. 기준일 t 이전에 공개된 정보만 사용 (라벨 누수 방지)
- 단계별 실패 로그 기록. 실패한 단계 이후의 mart는 직전 값 유지

단계 목록 보완 필요 사항

- `run_all.py`의 `STEPS` 주석에 아키텍처 문서의 `market_volatility` 단계가 없고, 기획안 필수 데이터인 ECOS 국고채 금리·기업기본정보 수집 단계도 없음 → `market_volatility`, `collect_ecos`, `collect_corp_info` 추가 제안
- 관리종목 지정 이력, 시장조치, 거래정지, 금리, 기업정보를 담을 raw 테이블이 계획된 `raw_*` 목록에 없음 → 7장에 테이블 추가 제안
- 일 단위 단계(1\~4, 9, 10)와 주 단위 단계(5\~8)가 한 진입점에 섞여 있음 → `run_all.py --schedule daily|weekly` 또는 단계 선택 인자 추가 제안
- KIND는 클라우드 IP 접속 차단이 확인됨(이슈 #4) → `collect_kind`는 국내 IP 환경(팀원 PC)에서 실행하고 적재 결과만 이전. EC2에서 접속 가능한지는 미확인이며, 불가하면 F-23 자동 갱신과 F-26 ④(시장조치 신규 지정)의 일 단위 반영이 수동 실행에 의존
- KIND 관리종목·투자주의환기·거래정지 메뉴는 기간 조회 없이 현재 목록만 제공 → 매일 스냅샷을 적재하고 직전 스냅샷과 비교해 지정·해제일 생성 (제안). 서비스 시작 이전의 과거 지정 이력은 KIND 공시 상세검색의 "관리종목지정" 공시로 수집 (2015년 이후 2,396건 확인, `pipeline/collect/kind_managed_disclosures.py`)
- 거래정지 목록에 ETF·ETN이 포함되므로 주식만 필터링. 투자주의·경고·위험 이력은 1회 조회가 3년 이내로 제한되므로 기간을 나눠 조회
- 5단계의 공시 이벤트 변수(유상증자·CB·BW 횟수 등)는 9단계 LLM 결과가 아닌 DART 공시 유형·보고서명 규칙으로 산출해야 단계 순서가 성립함

- 기준일 2016\~2025년 4월 1일 10개 시점의 양성 기업 수 (①·③ + ②): 12개월 창 584개, 15개월 창 688개. 검토 필요 분류(사유 불명 "상장폐지사유 발생" 323건, 정기보고서 미제출, 회생·파산·부도, 주가 미달) 포함 시 922개, 1,101개 (`docs/data_spec.md` 부실 라벨 건수 집계)
- 아직 반영하지 않은 학습 제외(기준일에 이미 관리종목·거래정지, 금융업·SPAC·리츠·외국기업)를 적용하면 건수가 줄어듦
- 상장폐지 사유는 자유 텍스트(2015년 이후 130종)이므로 사유 → 분류 코드 매핑 표를 `shared/`에 두고 키워드 규칙으로 1차 분류, 미분류 건은 수작업 검수
- 우선주(종목명 "우" 접미사)와 SPAC("스팩") 제외. 합병·해산 사유는 라벨 미확정으로 학습 제외

Merton 부도거리 (제안: 부도점 D = 단기부채 + 0.5 × 장기부채, r = ECOS 국고채 금리, T = 1년)

```latex
DD = \frac{\ln(V/D) + (r - \sigma_V^2/2)\,T}{\sigma_V \sqrt{T}}
```

- 자산가치 V와 자산변동성 σ\_V를 시가총액·주가 변동성에서 반복 계산할지, 단순화 근사를 쓸지는 미정

```python
GRADES = ['양호', '관찰', '주의', '경고']
BOUNDS = [('관찰', 0.5), ('주의', 2.0), ('경고', 5.0)]  # 기저율 배수, 예시값


def _grade(prob: float, base_rate: float, scale: float = 1.0) -> str:
    grade = '양호'
    for name, multiple in BOUNDS:
        if prob >= base_rate * multiple * scale:
            grade = name
    return grade


def assign_fin_grade(prob: float, base_rate: float, prev_grade: str | None, margin: float = 0.10) -> str:
    '''보정 확률을 4단계 등급으로 변환. 위험 감소는 경계값보다 margin만큼 더 낮아야 반영'''
    raw = _grade(prob, base_rate)
    if prev_grade is None or GRADES.index(raw) >= GRADES.index(prev_grade):
        return raw
    relaxed = _grade(prob, base_rate, scale=1.0 - margin)
    return GRADES[min(GRADES.index(prev_grade), GRADES.index(relaxed))]
```

- 예: 직전 "주의"(경계 2.0배)에서 1.9배로 내려오면 "주의" 유지, 1.8배 미만으로 내려와야 "관찰"로 변경 (T-19)

요인 설명 문구 규칙 (F-05)

- SHAP 요인은 인과로 읽히지 않도록 "모델 예측에 영향을 준 주요 요인"으로 표기
- 등급 경계까지의 거리 문구(예: "자본잠식률이 50%를 넘으면 한 단계 올라갈 수 있어요")는 등급 기준값이 확정된 뒤에만 노출
- 요인 문장의 수치도 종합평가 리포트와 같은 수치 일치 검증 대상

- 거래정지 구간: 거래량 0인 날(시가·고가·저가 0 또는 종가가 직전 값으로 유지)은 수익률 계산에서 제외. 제외 후 120거래일이 채워지지 않으면 확보된 기간으로 계산하고 실제 기간을 함께 표시 (제안)
- 기준값: 1.9 / 2.6 / 3.3은 최근 5년 20·40·60% 분위수, 마지막 경계는 80% 분위수(4.4%) 대신 5.0%로 조정 (팀 결정, 시장 변동성 배너 경고 기준과 같은 값). 고변동 시기가 분포에 들어가 기준값이 크게 잡힐 수 있으므로 운영 시 주기적으로 재계산
- 화면 기간 표시: 주가 변동 지표를 모두 최근 6개월(120거래일)로 통일. "최근 6개월 기준이며 미래를 보장하지 않음" (팀 결정)
- 시장 급변기에는 여러 종목의 등급이 함께 오르고 F-26 ③(주가 변동 "매우 높음")으로 선정되는 종목이 늘 수 있음 → 결론·카드 영역에 배너 상태를 함께 표시해 시장 전체 영향임을 안내 (제안)

시장 변동성 배너 (F-29)

| 항목 | 명세 |
| --- | --- |
| 지표 | KOSPI 최근 20거래일 일별 수익률 표준편차. 종목 등급(120거래일)보다 짧게 잡아 급변을 빠르게 반영 |
| 상태 기준 | "주의"는 과거 10년 분포 상위 10%(2.1%) 이상, "경고"는 5.0% 이상(팀 결정, 종목 등급 "매우 높음" 기준과 같은 값), 그 외 "표시 안 함" |
| 해제 기준 | 상위 20%(1.4%) 밖으로 내려가야 해제. 기준선 근처에서 매주 켜졌다 꺼지는 현상 방지 |
| 경고 → 주의 | 결산 시점 변동성이 5.0% 미만이고 해제 기준 이상이면 "주의"로 하향 |
| 기준값 갱신 | 주의·해제는 분위수에 해당하는 값을 연 1회 계산해 고정, 경고는 5.0% 고정. 고변동 시기가 지나 분포가 바뀌면 주기적으로 재계산해 고침 |
| 최근 이력 | 배너가 꺼져 있어도 직전 결산 주에 주의·경고였으면 작은 문구로 안내 ("지난주 시장 변동성 주의 구간") |
| 갱신 | 매주 토요일 결산. 그 주 마지막 거래일 종가 기준으로 상태를 정하고 다음 결산까지 유지, 기준일 표시 (팀 결정) |
| 휴장일·수집 실패 | 그 주 마지막 거래일 기준으로 결산. 수집 실패 시 직전 결산 상태와 기준일 유지 |
| 확인 결과 | 2020년 3월·2024년 8월·2025년 4월 급락은 "주의", "경고"는 2026년 7~8월(6주)뿐. 2026년 48주 중 43주 표시 문제는 화면 작업 때 표시 방식과 함께 확정 |

상태 판정 구현 예시 (제안)

```python
import numpy as np

WARNING_LEVEL = 5.0  # 경고 기준 (일 변동성 %, 고정)
CAUTION_QUANTILE = 0.90  # 주의: 과거 10년 분포 상위 10%
RELEASE_QUANTILE = 0.80  # 해제: 상위 20%


def banner_thresholds(history_vol: np.ndarray) -> dict[str, float]:
    '''연 1회 계산 후 연중 고정. history_vol: 과거 10년 KOSPI 20거래일 변동성 시계열'''
    return {
        '경고': WARNING_LEVEL,
        '주의': float(np.quantile(history_vol, CAUTION_QUANTILE)),
        '해제': float(np.quantile(history_vol, RELEASE_QUANTILE)),
    }


def next_banner_state(vol: float, prev_state: str, th: dict[str, float]) -> str:
    '''매주 토요일 결산: 그 주 마지막 거래일 종가 기준 20거래일 변동성으로 배너 상태 판정'''
    if vol >= th['경고']:
        return '경고'
    if vol >= th['주의']:
        return '주의'
    if prev_state in ('주의', '경고') and vol >= th['해제']:
        return '주의'
    return '없음'
```

- 예: 해제 기준과 주의 기준 사이 값은 직전 상태가 "주의"·"경고"면 "주의" 유지, 직전 상태가 "없음"이면 "없음" 유지

### 6-5. 포트폴리오 평가 (F-02, F-08\~F-10, F-26)

1. 입력 검증: 종목명·6자리 종목코드를 `corp_code`(DART 8자리)로 매핑, 수량은 양의 정수, 같은 종목은 합산. 없는 종목은 제외하고 안내 후 나머지 처리 (T-02). 빈 포트폴리오는 평가 차단 (F-22)
2. 비중 변환: 최신 종가 × 수량 ÷ 합계. 거래정지 종목은 마지막 종가 사용. 수량은 비중 산출 후 세션·DB에 저장하지 않음 (제안: 비중만 보관)
3. 조회: 최신 mart\_market\_volatility(배너 상태, 직전 결산 주 상태)와 종목별 최신 기준일의 `mart_fin_risk`, `mart_market_risk`, `mart_disclosure_labels`
4. 지표 계산 (아래 표)
5. 2×2 위치 판정: 재무 위험 "주의" 이상, 주가 변동 위험 "높음" 이상을 각 축의 "높음"으로 봄
6. 살펴볼 종목 선정: 아래 5개 기준 중 하나라도 해당하면 선정하고, 해당 사유를 카드에 표시
7. 직전 평가 대비 변화 (로그인 사용자): 지표 증감, 축별 등급 변경 종목

| 비중 산출 가격 | 직전 거래일 종가 × 수량. 거래정지 종목은 마지막 종가 | "비중은 YYYY-MM-DD 종가 기준" |
| 비중 가중 재무 위험 확률의 분모 | 평가 제외·데이터 부족 종목을 뺀 나머지 비중 합으로 나눠 재정규화. 재정규화하지 않으면 제외 비중만큼 위험이 낮게 보임 | 제외 종목 수와 비중을 별도 표시 |
| 포트폴리오 변동성·MDD·베타·상관 | 현재 비중을 최근 6개월간 고정했다고 가정한 일별 수익률로 계산 (매일 재조정 가정) | "현재 비중을 최근 6개월에 적용한 결과" 안내 |

- 세 항목 모두 팀 확정 후 지표 정의서와 테스트 기대값에 반영 (11-2)

### 6-6. 종합평가 리포트 (F-11)

1. 지표 계산 결과를 구조화 JSON으로 생성 (종목별 두 축 등급, 재무 위험 요인, 주가 변동 지표 포함)
2. LLM에는 JSON 수치와 종목 위험 요인만 전송. 수량·금액·닉네임·`user_id`·세션 식별자는 전송 금지
3. 수치 일치 검증: 생성 문장의 수치(%, 배, 단계명)를 추출해 JSON 원본과 반올림 허용 범위 내에서 대조. 불일치 시 재생성, 재시도 한도(제안: 2회) 초과 시 템플릿 문장으로 대체
4. 금칙어 필터: "매수", "매도", "비중을 늘리세요" 등. 목록은 `shared/`에서 관리
5. 원문 근거 인용을 포함한 형태로만 저장 (순환 오염 방지)
6. 저장: 체험 모드는 세션 메모리, 로그인 사용자는 `user_reports` + `user_docs` 임베딩

- LLM 호출 실패 시 지표·차트는 정상 응답하고 리포트 영역만 재시도 안내 (T-03)
- 품질 목표: 표본 50건 수치 일치율 95% 이상, 매매 권유 표현 0건

### 6-7. RAG 챗봇 (F-13\~F-20, F-25)

1. 요청 수 제한 확인 (`LLM_DAILY_REQUEST_LIMIT`, 기본 20)
2. 매매 권유 질문 판별 → 해당 시 매매 판단은 거절하고 관련 위험 근거만 안내 (F-18, T-06)
3. 질문에서 종목·기간 추출 → 메타데이터 필터 생성
4. `public_docs` 검색. 로그인 사용자는 `user_docs`를 서버 세션의 `user_id`로 필터해 검색, 체험 모드는 세션 메모리의 임시 리포트 검색
5. 결과 병합·재정렬 (리포트는 기준일 최신순 가중). 유사도 기준 미만이면 "확인 가능한 근거가 없습니다" 응답 (F-16)
6. 질문 + 근거 청크로 답변 생성. 사실 주장에는 공식 원문 인용 강제, 내 평가 리포트는 "지난 평가 내용"에만 사용 (F-15)
7. 후처리: 인용 존재 확인, 출처 카드 생성 \[공시\] \[보도자료\] \[내 평가 리포트(AI 생성)\] (F-14)
8. 챗봇 답변은 RAG 자료로 재저장하지 않음

- 대화 맥락(F-19)은 세션 단위로 유지. 화면 이동·창 닫기 후에도 세션 동안 유지 (F-25)
- 질문 유형 라우팅(F-20, 심화): 수치 질문은 DB 조회, 서술 질문은 RAG로 분기
- 품질 목표: 질문 40건 근거 일치 80% 이상, 출처 유형 표기 100%, 거절 대상 15건 중 13건 이상 거절, 타 사용자 리포트 검색 0건

* 출처 카드는 모든 출처에 기관명과 원문 링크를 표시하고, 출처별 이용 조건(7-5)에 따라 금감원 원문 링크는 사전 통지 후 사용, 한국거래소 자료는 원문 재게시 없이 짧은 인용과 링크만 표시

### 6-8. 세션·계정 (F-01, F-03, F-12)

| 기능 | 명세 |
| --- | --- |
| 체험 모드 | 로그인 없이 시작. 포트폴리오·리포트·챗봇 대화는 서버 세션에만 보관, 종료·만료 시 삭제. 만료 시간 미정 |

| 데이터 삭제 | 사용자 행(`user_portfolios`, `user_reports`, `users`)과 `user_docs` 벡터를 함께 삭제, 이후 챗봇 검색 0건 (T-10). 계정(users 행) 자체의 삭제 포함 여부는 미정 |

| 일별 주가 | 금융위 API 최근 5년: 약 2,900종목 × 연 250거래일 × 5년 ≈ 360만 행. FinanceDataReader 2015년 이후 과거 수정주가는 별도 (추정) |
| RAG 공용 문서 | 최근 2\~3년 위험 유형 공시, 최근 5년 보도자료 |
| RAG 개인 문서 | 사용자당 평가 횟수만큼 |

### 7-4. 데이터 품질 규칙

- 계정과목명 불일치: 주요 계정 매핑 테이블 작성. 연결·별도 중 사용 기준은 미정
- 감자·분할에 따른 주가 불연속: FinanceDataReader는 수정주가 제공. 금융위 API는 수정주가가 아니므로 상장주식수 변화로 분할·병합 보정 후 사용하고, 두 출처 종가 비교로 보정 결과 검증 (예: 카카오 2021-04 액면분할 시 금융위 종가 558,000원 → 120,500원)
- 거래정지 구간: 두 출처 모두 행이 남고 종가가 직전 값으로 유지됨. 거래량 0인 날은 수익률 계산에서 제외
- 생존 편향: 폐지 종목 목록을 먼저 확보하고 해당 기업 우선 수집
- 상장폐지 사유 필터: 합병·자진 폐지는 KIND 사유로 걸러 부실 라벨에서 제외

* KIND 지정 사유는 코드 없는 자유 텍스트이고 여러 사유가 쉼표로 연결됨 → 재무·비재무 사유 문구 사전과 분리 규칙을 `shared/`에 둠
* 매매거래정지 목록에는 정지일 컬럼이 없음 → 처음 관측된 스냅샷일을 정지일 근사값으로 사용 (제안). ETF·ETN 행은 제외

### 7-5. 출처별 이용 조건과 서비스 표시 방식

| 출처 | 이용 조건 (`docs/data_spec.md`) | 서비스 표시 방식 |
| --- | --- | --- |
| 금융위원회 홈페이지 | 비상업 자유이용, 출처 표시 | 짧은 인용 + 기관명 + 원문 링크 |
| 정책브리핑 | 텍스트에 한해 공공누리 제1유형 (출처 표시) | 짧은 인용 + 기관명 + 원문 링크 |
| 금융감독원 (보도자료 API, 소비자경보) | 비영리 개인 이용, 정당한 범위 인용, 출처 표시, 내용 무단 변경 금지. 다른 사이트에서 직접 링크 시 금감원에 링크 사실 통지 필요 | 서비스 공개 전 링크 통지, 이후 짧은 인용 + 원문 링크 |
| 한국거래소·KIND | 사전 동의 없는 복제·전송·배포 금지 (법적고지), robots.txt 없음 | 원문 재게시 금지. 가공 결과(등급, 사유 분류)와 원문 링크만 표시, 인용은 최소화 |
| FinanceDataReader | 기본 출처가 네이버 증권 시세이므로 네이버 이용약관 적용. 내부 분석·학습용 사용으로 결정 (팀 결정) | 내부 분석·학습용으로만 사용, 화면 시세 표시는 금융위 API 기준 |
| DART, 공공데이터포털, ECOS | 근거 문서에 정리되지 않음 | 확인 후 `docs/data_spec.md`에 기록 |

## 8. 인터페이스·외부 연동 명세

외부 연동은 데이터 API 4종, 크롤링 대상 사이트, LLM API 2종이며, 내부 Backend API는 아직 정의되지 않아 아래에 초안을 제안함. 가이드 기준으로 2주차 안에 API 명세 합의가 필요함.

### 8-1. 외부 연동

| 대상 | 용도 | 호출 위치 | 인증 | 실패 시 처리 |
| --- | --- | --- | --- | --- |
| DART OpenAPI | 재무제표, 공시 목록·원문 | `pipeline/collect` | `DART_API_KEY` | 실패 로그, 직전 적재 데이터 유지 |
| 공공데이터포털 | 주가, 지수, 기업기본정보 | `pipeline/collect` | `DATA_GO_KR_API_KEY` | 동일 |
| 한국은행 ECOS | 국고채 금리, 경기 지표 | `pipeline/collect` | `ECOS_API_KEY` | 동일 |
| 금융감독원 보도자료 API | 보도자료 (JSON, 본문 텍스트 포함) | `pipeline/collect` | `FSS_API_KEY` (32자리, 금감원 홈페이지에서 신청) | 동일 |
| KRX KIND | 관리종목·투자주의환기·거래정지, 투자주의·경고·위험, 실질심사, 횡령 등 | `pipeline/collect` (국내 IP 환경) | 없음 | 클라우드에서 차단되면 국내 환경 수집 결과를 이전 |
| 금융위 홈페이지, 금감원 소비자경보, 한국거래소, 정책브리핑 | 보도자료·소비자경보 | `pipeline/collect` | 없음 | 사이트별 파서 분리, 재시도, 구조 변경 시 실패 로그 |
| OpenAI API, Gemini API | 배치: 분류·요약·임베딩 / 실시간: 종합평가·챗봇 | `pipeline/llm`, `backend` | `OPENAI_API_KEY`, `GEMINI_API_KEY` | 배치: 재시도 후 미처리 표시 / 실시간: 해당 영역만 재시도 안내 |

- DART는 개인 키 일 20,000회 (OpenDART 안내 기준). 재무제표·감사의견 전체 수집은 약 54,000회로 최소 3일 분할 수집. 그 밖의 API 한도는 확인 후 `docs/data_spec.md`에 기록

### 8-2. LLM 전송 데이터 계약

| 호출 | 전송 항목 | 전송 금지 |
| --- | --- | --- |

설계 결정

- 지표 계산(`/evaluations`)과 LLM 리포트 생성(`/narrative`)을 분리함. 화면은 지표를 먼저 그리고 리포트는 로딩 표시 후 채움. LLM 실패가 지표 응답에 영향을 주지 않음 (T-03)
- `user_id`는 요청 본문·쿼리로 받지 않고 서버 세션에서만 읽음 (F-17)
- 상태 변경 요청(PUT·POST·DELETE)은 세션 쿠키 기반이므로 CSRF 대응 필요 (`SameSite` 쿠키 + CSRF 토큰)

* 시장 변동성 배너 상태는 평가 응답(`market_banner`)에 포함하고, 평가 전 화면용으로 `/api/market/volatility`를 따로 둠. 배너 상태 조회 실패는 오류로 노출하지 않고 배너를 숨김 (제안)

공통 응답 규칙 (제안)

- 경로 앞에 버전 접두어 `/api/v1`을 붙여 응답 계약 변경 시 병행 운영 가능하게 함 (위 표는 접두어 생략)
- 모든 응답에 `request_id`, `as_of`(데이터 기준일), `data_status` 포함

| `data_status` | 의미 | 화면 처리 |
| --- | --- | --- |
| `ok` | 모든 데이터 정상 | 기본 표시 |
| `partial` | 일부 종목·영역 데이터 누락 | 정상 부분 표시, 누락 부분에 사유 |
| `not_available` | 요청 데이터 없음 (신규 상장, 금융업 등) | 등급 외 상태 표시 |
| `stale` | 수집 실패로 기준일이 갱신 주기보다 오래됨 | 기준일 강조 + "갱신 지연" 표시 |

- 오류 응답은 사용자용 메시지와 내부 추적용 오류 코드를 분리하고, 내부 정보(스택, SQL)는 노출하지 않음
- 평가 결과에 데이터 기준일과 산출 기준 기간(예: 최근 6개월, 120거래일)을 포함

## 9. 설정 및 실행 환경

현재 `docker compose up -d`로 실행되는 것은 PostgreSQL 컨테이너 하나이며, `run_all.py`는 단계가 비어 있어 아무 작업도 하지 않음. 아래는 환경변수 정의와 목표 실행 구성임.

### 9-1. 환경변수 (`.env.example` 기준)

| 변수 | 용도 | 사용 위치 | 비고 |
| --- | --- | --- | --- |
| `DART_API_KEY` | DART OpenAPI | pipeline |  |
| `DATA_GO_KR_API_KEY` | 공공데이터포털 | pipeline |  |
| `ECOS_API_KEY` | 한국은행 ECOS | pipeline |  |
| `FSS_API_KEY` | 금융감독원 보도자료 API | pipeline | 32자리 인증키. 금감원 홈페이지 OPEN API에서 신청 |
| `OPENAI_API_KEY`, `GEMINI_API_KEY` | LLM·임베딩 | pipeline, backend |  |

### 9-2. 실행 절차 (README 기준)

```bash
cp .env.example .env        # 값 입력
docker compose up -d        # 현재는 db만 실행
python pipeline/run_all.py  # 현재는 STEPS가 비어 있음
```

- 호스트에서 `run_all.py`를 직접 실행하면 `POSTGRES_HOST=db`를 해석하지 못함. 파이프라인을 Compose 서비스로 실행하거나 호스트 실행 시 `POSTGRES_HOST=localhost`로 덮어써야 함

| `pipeline` | 저장소 루트 컨텍스트로 빌드 (`ml/` 포함) | - | 배치 (`docker compose run --rm pipeline`) | - |

- 모든 상시 서비스 `restart: unless-stopped`. EC2 보안 그룹은 80(및 관리용 22)만 개방
- backend 이미지에는 ML 라이브러리 불필요 (SHAP 요인은 `mart_fin_risk`에 저장된 값을 문장화). 컨테이너별 의존성 파일 분리로 이미지 크기 축소
- Python 버전과 의존성 버전은 컨테이너별 `requirements.txt`에 고정

`docker-compose.yml` 보완 예시 (제안)

```yaml
services:
  db:
    image: postgres:16
    restart: unless-stopped
    environment:
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    ports:
      - "127.0.0.1:5432:5432"  # 로컬 개발용. EC2에서는 제거
    volumes:
      - db_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 10s
      timeout: 5s
      retries: 5

  backend:
    build: ./backend
    restart: unless-stopped
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
    expose:
      - "8000"

  pipeline:
    build:
      context: .
      dockerfile: pipeline/Dockerfile
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
    profiles: ["batch"]  # docker compose up에서는 시작하지 않음

volumes:
  db_data:
```

- 변경 의도: db 컨테이너에 API 키 전달 중단(`env_file` → 필요한 3개 변수만), db 포트 외부 노출 차단, db 준비 완료 후 backend 시작, 파이프라인은 필요할 때만 실행
